1Summary & evaluation map

The platform is one generic engine. Each business process (loan approval, insurance claims, vendor onboarding, employee onboarding) is a versioned JSON workflow. A request is validated, made idempotent, pinned to the workflow version active at intake, and moved stage by stage. A stage optionally calls an external dependency, evaluates its rules and checkpoints atomically. The request ends in APPROVED, REJECTED or MANUAL_REVIEW, or parks in RETRY_PENDING when a dependency is down.

2Problem structuring

The difficult part is not evaluating an if. It is making decisions that stay correct, repeatable and explainable while inputs are bad, dependencies fail, clients retry and requirements change. I split the problem into five concerns, each with a single owner, so a change in one never touches the others:

ConcernQuestionOwnerChanges when…
What to decideWhich checks, thresholds, branches?Workflow JSONbusiness policy changes
How to evaluateDoes this rule pass for this data?rules.py, conditions.py (pure)a new operator is needed
When / orderNext stage? retry? stop?service.py, lifecycle.pyorchestration semantics change
RememberWhat happened, and can we prove it?store.pydatabase changes (SQLite → Postgres)
Outside worldHow to call flaky services safely?dependencies.pya real integration replaces a simulator

Out of scope (explicit): authentication and authorisation, multi-tenancy, a rule-authoring UI, and real third-party APIs. They are simulated behind the same interface a real client would implement.

3Architecture

Dependencies point downward only. The rule engine is pure (no I/O, clock or randomness), which is what makes checkpoint/resume safe and decisions reproducible. app.py is the composition root, the only module that names concrete classes.

ModuleResponsibility
schema.pyJSON-Schema subset validator. Returns all errors so clients fix a payload in one round trip. Also self-checks schemas at config load.
conditions.pyDeclarative condition DSL (13 operators, all/any/not, derived thresholds via {"ref","multiply"}). Evaluation returns a full trace; a static checker rejects unknown operators or fields.
rules.pyEvaluates the rules of a stage (guard → condition → effect). The outcome is the most severe effect: reject > review > pass. Also resolves conditional branches.
config.pyWorkflow model, load-time validation (references, cycles, reachability, duplicates), immutable versions, atomic hot reload, activation and rollback.
lifecycle.pyThe state machine. The only code that knows legal status transitions.
dependencies.pyGateway with real timeouts, bounded retries using exponential backoff and full jitter, and a circuit breaker per dependency. Includes 3 simulators and a FaultInjector (transient, permanent, timeout, outage, latency).
store.pyTransactions, optimistic locking, UNIQUE idempotency, processing leases, hash-chained audit, dependency-result cache, and storage fault injection.
service.pyOrchestrator: intake, replay, stage loop, checkpoints, diversion policies, retry and recovery sweep, human review, explain, simulate.
api.py / __main__.pyThin transport. Maps typed errors to HTTP codes (404/409/422/503), never leaks stack traces, emits structured logs.

4Data flow of one request

  1. Intake. POST /workflows/loan_application/requests with an optional Idempotency-Key.
  2. Idempotency. Look up (workflow, key).
    • Same payload hash: return the stored result (HTTP 200, Idempotent-Replay: true).
    • Different hash: HTTP 409.
    • No key: the canonical payload hash is the key.
  3. Validate. Check the schema and collect every error. Invalid requests are persisted as INVALID, audited and answered with 422.
  4. Pin and persist. Store workflow_version and config_hash with the request. Request row, history and audit are written in one transaction. The UNIQUE constraint settles concurrent duplicates.
  5. Lease. A conditional UPDATE acquires a processing lease, so only one worker handles a request.
  6. For each stage:
    • Fetch. Reuse a cached dependency result if one exists. Otherwise call the gateway, then persist the result and attempt log in their own transaction.
    • Evaluate the rules. The function is pure and traced.
    • Resolve the transition.
    • Checkpoint atomically: current stage, the stage.evaluated audit entry with the full trace, and the decision if terminal.
  7. Dependency down. The fetch's on_unavailable policy decides:
    • retry: go to RETRY_PENDING with a configured backoff (30 s, 120 s, 600 s) until on_exhausted.
    • review: fail-safe to a human.
    • skip: continue without the data.
  8. Background worker. Runs due retries and resumes any request whose processor died (expired lease) from its last checkpoint.

5Request lifecycle

lifecycle.check() guards every status change. Terminal states are final: a second review of a decided request returns 409. Each transition writes a state_history row with the actor (api, engine, retry-worker or reviewer:<name>) and the reason.

6Configuration model

A workflow is a JSON document containing:

  • an input schema;
  • declared dependencies, each with a timeout and retry policy;
  • a workflow-level retry policy;
  • stages, each with fetches, rules (optional when guard, condition, on_fail of reject, review or flag) and transitions (fixed, or ordered conditional branches with a default).

Risk asks to tighten straight-through approval. loan_application.v2.json is added:

  1. Preview. POST /workflows/loan_application/simulate?version=1|2 shows the same applicant moving from APPROVED to MANUAL_REVIEW. Nothing is persisted.
  2. Deploy. POST /admin/reload. Reload is atomic: an invalid file is rejected and the old config stays live.
  3. In-flight requests stay pinned to v1, which is tested even across a retry.
  4. Rollback. POST /admin/workflows/loan_application/activate {"version":1}.

Static validation at load catches all of the following:

  • unknown operators and bad regexes;
  • fields outside the input., deps. and meta. namespaces;
  • dangling stage targets, cycles and unreachable stages;
  • branch lists without a default;
  • duplicate rule ids and undeclared dependencies;
  • edits to an already-published version.

Adding a new business process is a new file. employee_onboarding required zero lines of code.

FailureMechanismOutcome (tested)
Invalid / malformed inputSchema validation (all errors), JSON parse guard, 1 MB body cap422; persisted as INVALID; audited
Duplicate requestIdempotency key + canonical payload hashOriginal result, no re-processing
Concurrent duplicatesDB UNIQUE(workflow, key) + processing lease12 threads → 1 record, 1 bureau call
Key reused, new payloadHash comparison409 idempotency_conflict
Transient dependency error / timeoutReal deadline; retries with exponential backoff + full jitter (capped)Absorbed within the call
Sustained outageCircuit breaker (closed → open → half-open); workflow RETRY_PENDING with backoff scheduleFails fast; auto-recovers
Retries exhaustedretry_policy.on_exhaustedMANUAL_REVIEW (never stuck)
Permanent dependency errorNot retried; doesn't trip breakerStraight to review
Partial save (failure mid-transaction)One transaction per checkpoint; rollbackStays at last good stage; resumes; each stage audited exactly once
Crash after an external callPer-request dependency-result cache, written immediatelyResume never re-calls the service
Worker dies mid-flightLease with TTL + recovery sweepAnother worker resumes
Lost updateOptimistic locking (row_version)ConcurrencyConflict, not an overwrite
Bad config / infinite loopLoad-time validation, cycle detection, max_stepsRejected before it can decide anything
Why resume is safe: a decision is a pure function of (config version, input, dependency results), and all three are persisted. Re-running a stage after any failure therefore yields the same answer, and the atomic checkpoint ensures it is recorded once.

8Auditability & explainability

  • Hash-chained audit. Entries are chained per request: hash = sha256(prev_hash | seq | event | stage | data | ts). Every read of /audit re-verifies the chain. A test edits one row and gets broken_at_seq: 3.
  • Rule traces. stage.evaluated stores, per rule: actual value, expected value, derived-threshold source, guard result, effect and data_refs (exactly which fields the rule read).
  • Dependency records. dependency.called and dependency.failed store input, output and every attempt (outcome, error, backoff ms).
  • Reproducibility. Every request carries workflow_version and config_hash, so a decision can be replayed against the exact rules that made it.
  • Human decisions. Manual decisions record reviewer, notes and the system's original recommendation.

Audit events for a request that hit a bureau outage and recovered, in order:

request.received → validation.passed → stage.evaluated[eligibility] → dependency.failed[credit_assessment]
→ retry.scheduled → retry.started → dependency.called → stage.evaluated[credit_assessment]
→ stage.evaluated[affordability] → decision.made          (hash chain VALID, eligibility not re-run)

12Trade-offs

DecisionAlternativeWhy
JSON condition DSLEmbedded expressions / scripting; rules-engine libraryNo code execution, validated at load, diffable between versions, explainable value by value. Less expressive, but derived thresholds and composites cover the use cases.
Acyclic stage graphAllow loopsGuaranteed termination. Repetition (retries) belongs to the lifecycle, not the graph.
Stage-level checkpointsPer-rule, or noneRules are pure and cheap, so re-running a stage is free. Fewer writes than per-rule.
Persist dependency results immediatelyPersist at checkpointNever double-call a paid or side-effecting service after a crash.
Synchronous submit + async retry workerFully async queueOne round trip for the common case, async only for slow paths. The queue is the scale-out step (§14).
SQLite + stdlibPostgres + FastAPI + RedisZero setup for reviewers. Transactions, UNIQUE and conditional UPDATE map one-to-one onto Postgres.
Payload hash as fallback keyMandatory keyProtects naive clients from double submits. Cost: two identical payloads merge, which is accepted because clients can send keys.
Evaluate every rule (no short-circuit)Stop at first failureExplanations show every reason. The cost is negligible.
Fail-safe fallbacks (→ MANUAL_REVIEW)Auto-reject / auto-approveWhen information is missing a human decides. Configurable per workflow.
Immutable config versionsEdit in placeReproducible decisions and safe pinning of in-flight requests. Rollback is a pointer change.

13Assumptions

  • Requests are JSON objects of at most 1 MB. Seconds of latency are acceptable on the retry path.
  • External dependencies are read-only lookups, so caching their result per request is valid.
  • A human reviewer is available for MANUAL_REVIEW. Reviewer identity comes from the caller, since auth is out of scope.
  • Clock skew between workers is below the lease TTL (60 s).
  • Config authors are trusted, but configs are still validated, because typos are the common failure.

14Scaling considerations

PressureApproach
ThroughputAPI and workers are stateless; run N replicas. Leases and the UNIQUE constraint already make concurrent workers safe. On Postgres, use SELECT … FOR UPDATE SKIP LOCKED for the sweep.
Slow dependenciesReturn 202 + request_id and process from a queue (Kafka/SQS) partitioned by request id. The resumable stage loop maps directly onto a consumer.
Dependency protectionBreakers already exist per dependency. Add bulkheads (separate pools), per-dependency rate limits, and shared breaker state via Redis.
Audit growthThe log is append-only: partition by month and archive to object storage. Hash chains are per request, so partitions are independent.
Read loadExplanations derive from immutable rows: use read replicas and caching.
Config distributionImmutable versions published to a config store and cached by (workflow, version). Reload is atomic.
ObservabilityStructured request logs exist. Add metrics per workflow, stage and rule (decision mix, review rate, dependency latency, breaker state, retry backlog) and alerts.
